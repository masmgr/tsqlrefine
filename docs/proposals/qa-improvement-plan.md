# 品質保証強化プラン

> Implementation status (2026-07-18): the automated infrastructure in all three
> phases is implemented. The public corpus starts with repository-owned fixtures;
> third-party corpora and private dogfooding targets remain ongoing operational
> additions subject to their license and data-handling requirements. See
> [`docs/quality-assurance.md`](../quality-assurance.md) for commands and workflows.

tsqlrefine 自体の品質保証を強化するための実行プラン。各施策を「効果」「初期コスト」「維持コスト」で評価し、費用対効果の高い順に 3 フェーズへ分割する。

## 前提: 現状の QA 体制

- CI: ubuntu / windows の 2 OS マトリクスでビルド+テスト(約 2,700 件)、カバレッジ収集(ゲートなし)、脆弱性スキャン
- `TreatWarningsAsErrors=true` + Roslyn アナライザー(`AnalysisLevel=latest-recommended`)
- ルールごとのサンプル SQL(`samples/sql/`、約 80 ファイル)
- smoke-test スキル(手動実行)

品質リスクの残存領域: ①未知の入力でのクラッシュ ②ルール変更による誤検知/見逃しの回帰 ③format/fix によるユーザーコード破壊 ④公開契約(exit code / Plugin API / JSON 出力)の意図しない破壊 ⑤性能回帰。

## Phase 1: 即着手(合計 4–5 日、PR ごとの CI 増分 +2〜3 分)

安価で恒久的な自動ゲートを先に張る。以降のすべての開発が恩恵を受ける。

### 1-1. コーパステスト+診断差分レポート(2–3 日)

- ライセンス上取り込み可能な実世界 T-SQL を `tests/corpus/` に収集する
  - 初期候補: AdventureWorks / WideWorldImporters スキーマスクリプト(MIT)、First Responder Kit(MIT)、tSQLt(Apache-2.0)
  - sp_WhoIsActive は GPL-3.0 のため、初期コーパスからは除外する。追加する場合は他のコーパスとディレクトリを分離し、当該ファイルのライセンス表示と再配布条件を明示する
  - 社内・顧客環境の SQL、個人情報・接続情報を含む SQL、出典または再配布条件が不明な SQL は公開コーパスへ取り込まない
- `tests/corpus/THIRD_PARTY.md` または機械可読な manifest に、プロジェクト名、原著作者、原本 URL、取得元 commit SHA / tag、ライセンス、取り込みパス、変更有無、checksum、`minCompatLevel` をファイル単位で記録する。各ライセンスが要求する著作権表示・ライセンス文・NOTICE・変更表示を同梱する
- CI で全コーパスに lint を実行し、**未処理例外ゼロ**を fail 条件にする
- 診断結果(ルール ID、severity、メッセージ、開始/終了位置)をスナップショットとしてコミットし、PR で差分をレビュー可能にする。パスと改行を正規化し、ファイルパス・位置・ルール ID の順に決定的にソートして OS や列挙順による差分を防ぐ
- ルール変更の影響(検知 +N / −M 件)を可視化する。スナップショット差分は機械的に誤検知と断定せず、意図した変更かを PR でレビューする
- 費用対効果の根拠: ルール単体テストでは踏めない入力組合せを一括カバーし、以後のルール開発全件の回帰検知器として機能する。初期投資は回収が最も速い

### 1-2. ドキュメント/メタデータ整合性チェック(0.5 日)

- CI で `docs/Rules/REFERENCE.md` を再生成し、差分があれば fail(生成忘れ検出)
- メタテスト追加: 全ルールにドキュメント・サンプル SQL・プリセット割り当てが存在することを検証(ルール 140 件規模では目視は機能しない)

### 1-3. PublicApiAnalyzers + PackageValidation(0.5–1 日)

- `Microsoft.CodeAnalysis.PublicApiAnalyzers` を `TsqlRefine.PluginSdk` に導入。公開 API の変更が `PublicAPI.Unshipped.txt` の差分として PR に必ず現れる
- `EnablePackageValidation` + `PackageValidationBaselineVersion` で前リリースとのバイナリ互換を検証
- CLAUDE.md に明記済みの「公開契約」を人間の注意力から CI ゲートへ移す。初期コスト最小で、破壊時の損害(プラグイン作者への影響)が大きい領域

### 1-4. カバレッジラチェット(0.5 日)

- 収集済みカバレッジに「前回比で下げない」方式のチェックを追加(固定閾値より運用摩擦が少ない)

## Phase 2: format/fix の安全性保証(合計 4–6 日)

format/fix はユーザーのコードを書き換えるため、壊した場合の信頼毀損が最大の領域。Phase 1 のコーパス資産を再利用するため、順序依存がある。

### 2-1. フォーマッター冪等性・非破壊性テスト(2–3 日)

- プロパティ 1(冪等性): 既存の `FormattingIdempotencyPropertyTests` をコーパス全件+ランダム変異入力へ拡張し、`format(format(x)) == format(x)` を検証する
- プロパティ 2(字句・構文上の非破壊性): フォーマット前後の ScriptDOM トークン列を次の等価規則で比較する
  - `TokenType` とトークン順は完全一致
  - キーワードは大文字小文字を無視する(keyword casing による正当な変更を許容)
  - 識別子、引用識別子、文字列、数値、演算子は完全一致
  - 空白・改行は比較対象外とし、コメントは別途、欠落・改変がないことを検証する
- この検査が保証するのは字句・構文上の非破壊性であり、データベース実行時の意味の完全な同値性ではない
- 入力生成は samples/sql とコーパスへのランダム変異(トークン境界の空白・改行、コメント、キーワードの大文字小文字)から開始する。文字列リテラルや引用識別子の内容は変異させない。CsCheck 導入は変異生成が不足した場合の次段とし、初期は自前変異で十分

### 2-2. fix 健全性テスト(1–2 日)

- コーパス全件に fix を適用し、次を検証する
  - 出力が同じ `compatLevel` で再パース可能
  - 実際に適用された fix の対象診断が、同じ位置・内容で残らない
  - fix の再実行でテキストが変化しない、または定めた最大回数以内に収束する
  - `SkippedFixes` は直ちに失敗とせず、競合・適用不能などの理由別件数を記録する
  - 他ルールの新規診断は一律に fail とせず、診断差分スナップショットで意図した副作用かをレビューする

### 2-3. 契約・互換の残件(各 0.5–1 日)

- JSON 出力を `schemas/` のスキーマで検証するテスト+exit code の契約テスト
- compatLevel 110–160 の各互換レベルでコーパスをパースするマトリクステスト
  - 全レベルで未処理例外ゼロを要求する
  - 各ファイルの `minCompatLevel` 以上では構文エラーゼロを要求する
  - `minCompatLevel` 未満で発生する構文エラーは正常系としてレベル別スナップショットに記録する
- smoke-test スキル相当の E2E を release.yml に組み込み、パッケージング後の実バイナリで実行

## Phase 3: 継続監視(合計 2–3 日+運用)

効果はあるが即効性が低い、または維持コスト(CI 時間・人的コスト)が相対的に高いもの。Phase 1–2 の定着後に導入する。

### 3-1. ベンチマーク+性能回帰監視(1–2 日)

- BenchmarkDotNet で「大きめの実ファイル 1 本を全ルールで lint」を計測し、github-action-benchmark で閾値超過をアラート
- PR ごとではなく main への push 時のみ実行し、CI コストを抑える

### 3-2. ミューテーションテスト(1 日+週次 CI)

- Stryker.NET を `TsqlRefine.Rules` に限定し週次スケジュール実行。全プロジェクト・PR ごとの実行は CI 時間に対して効果が見合わない
- スコアは絶対値目標にせず、「新規ルールの生存ミュータント」を確認する運用にする

### 3-3. ドッグフーディング運用(仕組み 0.5 日+継続)

- 社内の実 SQL 資産に対して定期実行し、誤検知を issue 化するルーチンを確立
- ルール精度(誤検知率)のフィードバックは自動テストからは得られない唯一の情報源。人的コストがかかるため、頻度は隔週〜月次から開始

## 見送り(現時点で ROI が低いもの)

- **文法ベースのファジング(SQL 生成器の自作)**: コーパス+変異で当面のクラッシュ検出は賄える。生成器の構築・維持コストが高い
- **SonarQube / Qodana 等の外部静的解析**: Roslyn アナライザー(latest-recommended + warnings-as-errors)と重複が大きい
- **テレメトリ/クラッシュレポート収集**: ユーザー基盤の規模が正当化するまで保留

## 全体コストと期待効果

- 初期投資合計: 約 10–14 人日(Phase 1: 4–5 日 → Phase 2: 4–6 日 → Phase 3: 2–3 日)
- 継続コスト: PR ごとの CI +2〜4 分、週次ジョブ 1 本、ドッグフーディングの人的運用
- Phase 1 完了時点で「クラッシュ・検知回帰・API 破壊・ドキュメント乖離」が自動ゲート化され、Phase 2 完了時点で format/fix の字句・構文上の非破壊性と fix の収束性が機械的に検証される
